# 建筑领域风险场景执行流

## 〇、硬约束（先于一切流程，任何阶段不得违反）

**五条核心规则**：

| 规则 | 内容 |
|---|---|
| 证据优先 | 任何建议必须有证据支撑 |
| 时效红线 | 所有法定/约定期限必须标注并预警 |
| 书面留痕 | 所有对外沟通必须书面化 |
| 底线保护 | 绝不建议签署债务加入文件，绝不建议承认无依据责任 |
| 人机边界 | 重大决策必须提示"建议咨询专业律师" |

**甲方（建设单位）五项铁律**：

1. 不违约：任何暂停/扣留均以施工总承包合同明确约定为前提；
2. 不越权：不直接干预劳务合同、不直接清退分包；
3. 不伪造：严禁虚假签证、虚假设计变更；
4. 法定义务不可切割：欠付工程款范围内的先行垫付义务不因内部协议免除；
5. 内外效力分离：《责任切割协议》仅内部有效，不得对抗劳动者及监管部门。

**引用法规时使用全称+书名号+条号**（如《保障农民工工资支付条例》第三十三条），禁用《条例》等泛称。

## 一、总体架构：六阶段门控流

```
Phase 0   输入接收
  ↓
Phase 1   场景判断（三问链 + L3规则扫描）
  ↓  【欠薪类·事后/割离模式】
Phase 1.5~X   欠薪决策树（逐节点问答 + 材料验证）
  ↓  【情形定位完成】
Phase 2   新情形转化判定（能不能转 → 路径 → 闭环 → 硬边界）
  ↓
Phase 3   自检门控（三轮攻击）
  ↓  【校验通过】
Phase 4   方案输出（8要素 + 甲方立场 + 新情形动作）
  ↓
Phase 5   措施目标双轨判定
  ↓
Phase 6   持续监控 + 案件关闭复盘
```

## 二、Phase 0：输入接收

| 要素 | 说明 |
|---|---|
| 输入形式 | 用户自然语言描述 + 上传文件（合同、工资表、转账凭证等） |
| 实体提取 | 自动提取：项目名称、涉事主体（建设单位/总包/分包/劳务）、事件类型（欠薪/安全/质量/合规）、金额、时间节点 |
| 预分类 | 由 L1 本体层初步归类为：欠薪风险 / 安全风险 / 质量风险 / 进度风险 / 合规风险 |

## 三、Phase 1：场景判断（三问链 + L3 规则扫描）

执行 `references/risk-flow-logic.md` 的三问链，同时将输入事件与 `references/rule-engine.md` 做 if-then 匹配。

### 3.1 三问链（L0 入口层）

| 判断节点 | 问题 | 分支逻辑 |
|---|---|---|
| 判断1 | 建设单位做了没有？ | 没做 → 事前模式（避坑），跳转 Phase 4 直接输出避坑方案；做了 → 进入判断2 |
| 判断2 | 麻烦产生了没有？ | 没产生 → 事中模式（止损），进入 L3 规则扫描；产生了 → 进入判断3 |
| 判断3 | 建设单位有没有过错？ | 有过错 → 事后模式（担责+止损）；无过错 → 割离模式（自证+划界+追责+转嫁） |

### 3.2 L3 规则引擎同步扫描

| 规则簇 | 命中示例 | 后续路由 |
|---|---|---|
| 规则簇1（A1~A22） | 欠薪类风险 | 进入 Phase 1.5 欠薪决策树 |
| 规则簇2（B1~B5） | 安全风险 | 跳转 L4 策略簇2，直接生成安全降级方案 |
| 规则簇3（C1~C3） | 质量风险 | 跳转 L4 策略簇3，直接生成质量降级方案 |
| 规则簇4（D1~D3） | 进度风险 | 跳转 L4 策略簇4（如未详述，按通用止损处理） |
| 规则簇5（E1~E3） | 合规性风险 | 跳转 L4 策略簇4，直接生成合规降级方案 |
| 规则簇7/8（G/H） | 技术/环境风险 | 按通用止损/割离模式处理 |

**关键门控**：仅当命中 A 系列（欠薪风险）且模式为事后/割离时，才进入 Phase 1.5 的欠薪决策树。其他情形直接跳转 L4 生成方案。

## 四、Phase 1.5~X：欠薪决策树（逐节点推进 + 材料验证）

### 4.1 决策树总图

```
根节点 Q_money
├── 甲方有钱
│   ├── 有钱未付（Q_paid=未付）
│   │   ├── 产值未审（Q_valuation=未审）
│   │   │   ├── 未到进度（Q_progress=未达） → 情形一
│   │   │   └── 已达进度（Q_progress=已达） → 需审产值后转情形
│   │   └── 产值已审（Q_valuation=已审）
│   │       ├── 流程过长（Q_reason=流程） → 情形三
│   │       └── 其他原因（Q_reason=其他） → 情形四/五
│   └── 有钱已付（Q_paid=已付）
│       ├── 分账支付（Q_method=分账）
│       │   ├── 专户有余额（Q_account=有余） → 情形六
│       │   └── 专户无余额（Q_account=无余） → 情形七
│       └── 全额支付（Q_method=全额）
│           ├── 施工单位有分账（Q_split=有）
│           │   ├── 专户有余额 → 情形八（同六）
│           │   └── 专户无余额 → 情形九
│           └── 施工单位无分账（Q_split=无）
│               ├── 总包代发（Q_salary=代发）
│               │   ├── 专户有余额 → 情形十
│               │   └── 专户无余额 → 情形十一
│               └── 直接付分包（Q_salary=直付） → 情形十二
└── 甲方没钱（Q_money=没钱）
    ├── 欠一部分（Q_arrears=部分）
    │   ├── 前期有钱，当期没钱（Q_cashflow=当期断流）
    │   │   ├── 有分账 → 情形六/七
    │   │   └── 无分账 → 情形十/十一/十二
    │   └── 从未全额支付（Q_arrears=长期欠付）
    │       └── 无分账 → 情形十/十一/十二
    └── 从未支付（Q_arrears=全部） → 情形十三
```

**情形五特殊规则**：情形五是汇总节点，不可独立回答。用户说"我处于情形五"时，必须按 `references/situation-actions.md` 情形五的强制判断流程（①甲方有没有钱→②是否分账→③专户余额→④欠薪状态→⑤总包分账→⑥全额进度款→⑦支付方式）逐一提问，直到走到末端情形（六、七、九、十一、十二、十三）。

### 4.2 节点详细设计（问答 + 凭证验证）

**🔒 硬性规则（凭证门控）**：每个节点必须同时满足 ① 用户回答问题；② 用户上传该节点要求的凭证文件且校验通过，才解锁下一节点。**只回答、未上传凭证的，一律不得推进**——Agent 必须明确列出该节点缺失的材料清单（文件名+用途），等待用户上传后再继续。禁止仅凭口头回答推进决策树。

| 节点编号 | 节点名称 | 向用户提出的问题 | 用户可选项 | 本节点必须上传的材料 | 校验规则 | 下一节点 |
|---|---|---|---|---|---|---|
| N1 | Q_money | 建设单位（甲方）当前是否具备支付能力？ | A.有钱可付 / B.资金紧张但可筹措 / C.完全没钱 | ① 甲方最近一期财务报表或资金计划表；② 已付工程款银行流水或支付凭证 | 财务数据与自述一致 | A→N2；B/C→N12 |
| N2 | Q_paid | 甲方对总包的工程款是"已付"还是"未付"状态？ | A.已付（进度款已付） / B.未付（应付未付） | ① 施工总承包合同（付款条款页）；② 最近一期工程款支付凭证（如已付）或应付未付明细（如未付） | 合同条款与支付记录交叉核验 | A→N3；B→N4 |
| N3 | Q_payment_method | 已付款项是通过"分账支付"（人工费单独拨付至专户）还是"全额支付"（一笔总款打给总包）？ | A.分账支付 / B.全额支付进度款 | ① 银行转账凭证（查看备注/收款账户）；② 如为分账，需上传工资专户开户证明及流水 | 转账凭证收款账户名称核验 | A→N5；B→N6 |
| N4 | Q_valuation | 未付款项对应的产值是否已完成审核？ | A.产值未审 / B.产值已审 | ① 产值报审表；② 监理签字确认的进度确认单；③ 如已审，上传审定单 | 时间逻辑核验（报审→审核） | A→N4_1；B→N4_3 |
| N4_1 | Q_progress | 施工单位是否已达到合同约定的付款进度节点？ | A.未达到 / B.已达到 | ① 合同约定的进度节点条款；② 现场实际进度照片/监理日志；③ 甲方和监理的进度确认记录 | 合同条款与现场记录比对 | A→情形一；B→提示"需先完成产值审核" |
| N4_3 | Q_reason | 产值已审但未付的原因是什么？ | A.支付流程过长（财务审批/用款计划延迟） / B.其他原因（争议、故意拖欠等） | ① 产值审定单；② 甲方内部付款审批流截图/记录；③ 如存在争议，上传争议说明函 | 审定日期与当前日期差>30天标记为"流程过长" | A→情形三；B→情形四 |
| N5 | Q_account_split | 分账支付模式下，工资专户当前余额是否足以覆盖应付工资？ | A.专户有余额 / B.专户无余额 | ① 工资专户银行流水（最近3个月）；② 本月工资表（应付工资总额） | 流水余额 ≥ 工资表总额？ | A→情形六；B→情形七 |
| N6 | Q_split_by_contract | 全额支付模式下，总包是否将款项分账至工资专户？ | A.总包有分账（收到全款后自行拆分） / B.总包无分账 | ① 总包收款账户流水（查看进账后是否转出至专户）；② 工资专户流水 | 总包收款后是否有向专户转账记录 | A→N7；B→N8 |
| N7 | Q_account_full_split | 总包分账后，工资专户余额状态？ | A.专户有余额 / B.专户无余额 | ① 工资专户流水；② 工资表 | 余额与工资表比对 | A→情形八；B→情形九 |
| N8 | Q_salary_payment_method | 总包无分账时，工资是通过"总包代发"还是"直接付给分包"方式支付？ | A.总包代发 / B.直接付给分包单位 | ① 总包与劳务分包合同（代发条款）；② 工资表（显示发放主体）；③ 分包合同 | 合同条款与工资表发放主体比对 | A→N9；B→N10 |
| N9 | Q_account_salary | 总包代发模式下，工资专户余额状态？ | A.专户有余额 / B.专户无余额 | ① 工资专户流水；② 工资表；③ 代发银行流水 | 代发流水与工资表交叉核验 | A→情形十；B→情形十一 |
| N10 | Q_subcontract_paid | 分包单位收到款项后，是否已实际发放给农民工？ | A.已发放（工人已拿到钱） / B.未发放（工人被拖欠） | ① 分包单位向工人转账的银行流水；② 工人签字的工资表；③ 分包收款凭证 | 闭环确认：流水+签字表必须齐全 | A→情形十二-A；B→情形十二-B |
| N12 | Q_arrears | 甲方没钱属于哪种情况？ | A.前期有钱，当期没钱（阶段性断流） / B.从开工就未全额支付（长期欠付） / C.从未支付过（彻底停摆） | ① 项目开工至今全部工程款支付台账；② 甲方资金缺口说明；③ 如存在以物抵债意向，上传资产清单 | 支付台账与合同金额比对计算欠付比例 | A→N12_1；B→N12_2；C→情形十三 |
| N12_1 | Q_cashflow_split | 阶段性断流时，此前是否执行分账支付？ | A.有分账 / B.无分账 | ① 历史工资专户流水；② 历史支付凭证 | 历史流水核验 | A→N5（同分账路径）；B→N8（同无分账路径） |
| N12_2 | Q_longterm_method | 长期欠付时，工资支付方式？ | A.总包代发 / B.直接付分包 | ① 历史工资表；② 历史代发/分包付款流水 | 与 N8 逻辑一致 | 分别导向 N9/N10 |

### 4.3 节点门控机制（凭证优先，先证后答）

每个节点按以下顺序校验，任一不通过则不解锁下一节点：

1. **凭证上传校验（第一道硬闸）**：该节点要求上传的凭证文件未上传或上传不全时，明确列出缺失清单（文件名+用途），要求补充后再推进。**即使答案正确，凭证未上传也不解锁下一节点**；
2. **材料真实性初筛**：上传材料存在逻辑矛盾（日期倒置、金额不匹配、主体不符）时，暂停并要求核实后重新上传；
3. **答案校验**：回答必须在预设选项范围内，否则要求重新选择；
4. **解锁下一节点**：凭证完整且校验通过后，按选项路由推进。

## 五、Phase 2：新情形转化判定（四步判定）

决策树到达叶节点（情形定位完成）后，依据 `references/situation-actions.md` 执行：

| 步骤 | 名称 | 执行内容 | 输出物 |
|---|---|---|---|
| Step 1 | 能不能转 | 查情形汇总表，判定该情形属于 ❌不能 / ⚠️部分能 / ✅能 | 《转化可行性判定书》 |
| Step 2 | 转化路径 | 若"能转"或"部分能转"，提取对应转化路径（如垫付→签代付协议→结算抵扣） | 《转化路径操作指引》 |
| Step 3 | 闭环确认 | 核验工资是否真实进入工人账户（银行流水+签字工资表） | 《闭环确认核验报告》 |
| Step 4 | 专户硬边界 | 执行五项铁律之"法定义务不可切割"+ 专户余额绝对不能转 | 《专户合规边界确认书》 |

### 5.1 专户硬边界检查清单（Step 4）

| 检查项 | 规则来源 | 判定标准 |
|---|---|---|
| 专户资金是否被提议用于抵扣其他欠款？ | 《保障农民工工资支付条例》第三十三条 + 情形六说明 | 绝对禁止。若用户或方案中出现此意图，立即拦截并输出红色警告 |
| 专户余额是否被提议转入非农民工账户？ | 《暂行办法》第八条 | 绝对禁止 |
| 建设单位是否试图通过协议免除法定垫付义务？ | 五项铁律第4条 | 协议可约定内部追偿，但必须附加"法定垫付义务不免除声明" |
| 款项性质认定是否清晰？ | 降级引擎多项策略 | 每笔支付必须签订《款项性质认定书》，定性为"履行建设工程价款支付义务"而非"自愿垫付" |

## 六、Phase 3：自检门控（三轮攻击）

方案草稿完成后，按 `references/self-feedback.md` 执行三重攻击强制校验。任一攻击发现致命缺陷，必须回退修正。

### 6.1 攻击一：假设攻击（Assumption Attack）

| 检查项 | 攻击内容 | 判定标准 | 未通过时的回退动作 |
|---|---|---|---|
| H1-1 | 是否列出了方案依赖的所有关键假设？ | 至少列出 3 个关键假设 | 要求补充假设清单 |
| H1-2 | 每个关键假设是否有证据支撑？ | 无证据支撑的假设标记为"脆弱假设" | 要求补充证据或替换为有证据的假设 |
| H1-3 | 若最关键假设不成立，是否有 Plan B？ | 无 Plan B 视为"单点故障" | 要求设计替代路径（如主路径为"督促函"，备选路径为"直接代付"） |
| H1-4 | 是否质疑了输入数据的真实性？ | 对考勤、工资表、合同文本必须质疑 | 要求增加"工资表真实性核查"步骤（如与监理日志交叉比对） |

### 6.2 攻击二：逆向攻击（Reverse Attack）

以20年经验建筑法务/项目经理的视角审查方案：

| 检查项 | 攻击内容 | 判定标准 | 未通过时的回退动作 |
|---|---|---|---|
| H2-1 | 是否评估了追偿权的可实现性？ | 若追偿对象已失信/资金链断裂，必须标记 | 要求补充追偿权担保机制（如要求总包提供履约保函） |
| H2-2 | 是否考虑了方案对后续结算/诉讼地位的影响？ | 直接支付可能被认定为"承认债务"，必须评估 | 要求补充《款项性质认定书》明确支付性质 |
| H2-3 | 是否识别了"合规但愚蠢"的路径？ | 形式上合法、实质上加剧风险的路径必须剔除 | 剔除该路径，替换为实质更优方案 |
| H2-4 | 是否考虑了多主体利益冲突下的策略脆弱性？ | 至少分析建设、施工、劳务、农民工四方立场 | 要求补充四方利益博弈分析 |

### 6.3 攻击三：边界攻击（Boundary Attack）

| 检查项 | 攻击内容 | 判定标准 | 未通过时的回退动作 |
|---|---|---|---|
| H3-1 | 是否扫描了所有可能触发的关联规则？ | 至少扫描与核心风险同簇的所有规则 | 要求扫描 A 系列全部 22 条规则，检查是否遗漏（如 A20 失信清退） |
| H3-2 | 是否利用了 Ontology 关系层的信息？ | 如主体间信任度、资金链传导等隐性关系 | 要求补充资金链传导分析（如甲方拖欠→总包停发→劳务欠薪） |
| H3-3 | 是否考虑了时间/地域/政策的特殊约束？ | 如敏感时点、地方工资保障条例等 | 要求检索项目所在地地方性工资保障政策（如应急周转金） |
| H3-4 | 是否遗漏了"规则未覆盖但常识应知"的因素？ | 如劳务公司跑路风险、农民工春节返乡紧迫性 | 要求补充常识性风险因子 |

### 6.4 攻击输出格式

```
【自检门控报告】
攻击一：假设攻击
├─ H1-1 关键假设清单：[列出假设]
├─ H1-2 脆弱假设标记：[标记无证据的假设]
├─ H1-3 单点故障检查：[是否有Plan B]
└─ H1-4 数据真实性质疑：[是否质疑工资表/考勤]
攻击二：逆向攻击
├─ H2-1 追偿权可实现性：[评估结果]
├─ H2-2 结算地位影响：[评估结果]
├─ H2-3 合规但愚蠢路径：[识别结果]
└─ H2-4 四方利益冲突：[分析结果]

├─ H3-1 关联规则扫描：[是否遗漏A20等]
```

## 八、Phase 5：措施目标双轨判定

方案输出后，对"措施轨"与"目标轨"做对齐校验：

| 目标轨 | 措施轨（对应动作） | 校验逻辑 |
|---|---|---|
| 风险降级 | 发督促函、要求监理出通知单 | 若目标是降级，但措施仅为"内部签协议"，则判定为"措施不足"（协议不对外生效） |
| 责任切割 | 签《责任切割协议》+ 固定已履行义务证据 | 若仅有协议无证据，判定为"切割不牢" |
| 证据固化 | 签《款项性质认定书》、留存送达回执 | 若仅有口头沟通无书面留痕，判定为"证据脆弱" |
| 欠款转化 | 垫付→签代付协议→结算抵扣 | 若仅有《欠款确认》无实际支付，判定为"转化不彻底"（如情形十三） |
| 追偿保障 | 要求总包提供履约保函/担保 | 若追偿对象已失信且无担保，判定为"追偿权落空风险" |

**判定规则**：每项目标必须有 ≥1 项措施支撑；每项措施必须能追溯到至少一项具体目标；若出现"无目标支撑的措施"或"无措施支撑的目标"，触发回退修正。

## 九、Phase 6：持续监控 + 案件关闭复盘

### 9.1 持续监控机制

| 监控类型 | 触发条件 | 自动动作 |
|---|---|---|
| 时效监控 | 方案中存在法定/约定期限（如"限期3天开设专户"） | 到期前 24h 自动提醒用户 |
| 状态变更监控 | 原判定为"事中模式"，但用户反馈"工人已堵门" | 自动从"事中"升级为"事后"，重新触发 L3 规则扫描（A22） |
| 材料补全监控 | 决策树节点材料未上传完整 | 每 24h 提醒一次，超 72h 未补全则标记为"材料缺失，方案受限" |
| 敏感时点监控 | 当前日期进入"春节前30天"或"开学前15天" | 自动触发 A15 规则，升级风险等级并推送预警 |

### 9.2 案件关闭标准（满足任一即可关闭）

| 关闭类型 | 标准 | 复盘要求 |
|---|---|---|
| 正常关闭 | 欠薪事实消除（工人拿到钱）+ 欠款已转化或支付完毕 | 输出《案件复盘报告》：实际执行路径与初始方案的偏差分析 |
| 协议关闭 | 双方签署《欠款确认协议》+ 进入正常履约轨道 | 复盘协议履行跟踪节点 |
| 割离关闭 | 建设单位完成自证+划界+追责，且无后续牵连 | 复盘证据链完整性 |
| 强制关闭 | 进入仲裁/诉讼程序，Agent 职责移交法务 | 输出《证据封存清单》+《法务移交包》 |

## 十、异常分支与兜底机制

| 异常场景 | 处理逻辑 |
|---|---|
| 用户无法提供某节点材料 | 标记为"材料缺失，方案受限"，**暂停推进决策树（不解锁下一节点）**，基于现有材料生成"保守版方案"，并明确告知"因缺少XX材料，以下结论存在不确定性"；同时列出缺失凭证清单，待用户补齐后再继续走节点 |
| 用户回答与上传材料矛盾 | 触发"数据真实性质疑"（H1-4），暂停推进，要求用户解释矛盾点 |
| L3 规则扫描未命中任何规则 | 标记为"边界案例"，不强行匹配，输出："当前事件超出标准规则覆盖范围，建议人工研判"，同时启动通用止损/避坑流程 |
| 三轮攻击连续 3 次未通过 | 触发"人机边界"规则，输出："方案存在重大不确定性，建议咨询专业律师"，并生成《法务风险提示书》 |
| 涉及 E2/E3（阴阳/黑白合同） | 直接输出"无合法降级空间"，进入唯一可行措施：封存证据 + 报告法务，不进入决策树 |
