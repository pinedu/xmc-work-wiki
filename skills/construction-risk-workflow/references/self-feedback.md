# 自我反馈机制（三轮攻击）

> 本文件是 `construction-risk-workflow` skill 的参考文档。Phase 3 自检门控的攻击操作清单、判定标准、攻击示例与修正指令：攻击一假设攻击（H1-1~H1-4）、攻击二逆向攻击（H2-1~H2-4）、攻击三边界攻击（H3-1~H3-4）。

---

输出方案前需进行以下操作：

攻击一：假设攻击（Assumption Attack）
攻击目标：推理建立在哪些隐含假设上？如果这些假设不成立，结论是否崩塌？
触发条件（满足任意一条即启动）：

方案中包含"对方会配合""对方有能力履行"等预期


直接引用了某份文件（如工资表）的数据，但未质疑其真实性


将历史案例的结论迁移到本项目，但未说明迁移的前提条件


攻击操作清单：
表格
检查项编号	攻击内容	                                                 判定标准
H1-1	是否列出了方案依赖的所有关键假设？   	至少列出3个关键假设，缺一个即标记
H1-2	每个关键假设是否有证据支撑？	               无证据支撑的假设视为"脆弱假设"
H1-3	若最关键假设不成立，是否有Plan B？ 	无Plan B即视为"单点故障"
H1-4	主Agent是否质疑了输入数据的真实性？	对考勤、工资表、合同文本等关键数据，必须质疑

攻击示例：
markdown
【假设攻击报告】

主Agent方案依赖的关键假设：1. "工资表中的80人是真实用工人数"
   → 证据：无（直接引用工资表，未交叉核验）
   → 攻击：现场安全检查记录仅55人，差异45%。若该假设不成立，
           主Agent的支付方案将为25名虚报人员支付约62.5万元，且无法追偿。
   → 判定：❌ 脆弱假设，未质疑数据真实性
2. "施工单位收到督促函后会配合补足专户"
   → 证据：无（未分析施工单位历史配合度）
   → 攻击：某鑫达劳务已被列入失信名单，历史配合度极低。若该假设不成立，
           时间窗口将浪费3-5天，错过春节前最佳处置期。
   → 判定：❌ 脆弱假设，未评估对方履约意愿

修正指令：
· 要求在方案中增加"工资表真实性核查"步骤
· 要求将支付基准调整为"经监理确认的55人"
· 要求将路径A（督促函）降级为"保底动作"，主路径切换为路径B（直接代付）

攻击二：逆向攻击（Reverse Attack）
攻击目标：如果让一个有20年经验的建筑法务/项目经理来审查这个方案，他最可能质疑什么？
触发条件（满足任意一条即启动）：

方案完全依赖规则引擎的预定义路径，无创造性调整


未评估策略的可执行性（如对方履约能力、时间可行性）


未考虑方案的长期后果（如结算中的被动地位）


攻击操作清单：
表格
检查项编号	攻击内容	判定标准
H2-1	是否评估了追偿权的可实现性？	若追偿对象已失信/资金链断裂，追偿权大概率落空，必须标记
H2-2	是否考虑了方案对后续结算/诉讼地位的影响？	如直接支付可能被认定为"承认债务"，必须评估
H2-3	是否识别了"合规但愚蠢"的路径？	形式上合法、实质上加剧风险的路径必须剔除
H2-4	是否考虑了多主体利益冲突下的策略脆弱性？	至少分析建设、施工、劳务、农民工四方立场
攻击示例：
markdown
【逆向攻击报告】

20年经验法务最可能质疑的点：

质疑点1：追偿权可实现性未评估
· 建议签订《责任切割协议》，约定建设单位垫付后享有追偿权。
· 但追偿对象（某鑫达劳务）已被列入失信名单，且建工三公司自身也有专户管理问题。
· 这意味着追偿权在法律上存在，在事实上几乎无法兑现。
· 资深法务会质疑："你签了一份对方根本赔不起的协议，意义何在？"

质疑点2：代位清偿的结算风险未对冲
· 建议建设单位直接支付农民工工资（代位清偿）。
· 但未说明：该支付行为在后续结算中，施工单位可能主张"这是建设单位自愿垫付，不应抵扣工程款"。
· 资深法务会质疑："你付了钱，但有没有固定证据这笔钱是'履行工程款支付义务'而非'自愿垫付'？"

修正指令：
· 要求补充"追偿权担保机制"（如要求总包提供履约保函）
· 要求在支付前必须签订《款项性质认定书》，明确支付性质
· 要求同步启动《过程结算协议》，将已支付部分从争议金额中剥离

攻击三：边界攻击（Boundary Attack）
攻击目标：是否存在主Agent没有考虑到的规则、情境因素或更优替代方案？
触发条件（满足任意一条即启动）：

只使用了规则引擎中的部分规则，未扫描关联规则


方案未引用Ontology中已识别的关键关系（如主体间信任度）


未考虑时间、地域、政策等特殊情境因素


攻击操作清单：
表格
检查项编号	攻击内容	判定标准
H3-1	是否扫描了所有可能触发的关联规则？	至少扫描与核心风险同簇的所有规则
H3-2	是否利用了Ontology关系层的信息？	如主体间信任度、资金链传导等隐性关系
H3-3	是否考虑了时间/地域/政策的特殊约束？	如敏感时点、地方工资保障条例等
H3-4	是否遗漏了"规则未覆盖但常识应知"的因素？	如劳务公司跑路风险、农民工春节返乡紧迫性
攻击示例：
markdown
【边界攻击报告】

盲区1：未触发R-A20（用工主体失信清退义务）
· Agent专注于欠薪处置，完全忽略了《降级引擎》R-A20的规定：
  "用工主体被列入失信名单的，建设单位应要求总包清退该主体"。
· 这意味着：Agent的方案解决了"这次欠薪"，但未阻止"下次继续欠薪"
  （因为失信劳务公司仍在项目中，下个月还会产生新的欠薪）。
· 边界攻击结论：Agent的解决方案是"止痛片"，不是"手术"。

盲区2：未利用Ontology关系层的"资金链传导"信息
· Ontology已识别：城投置业拖欠4500万 → 建工三公司停发材料款 → 某鑫达欠薪。
· 但Agent的方案只处理了末端（欠薪），未处理源头（建设单位拖欠）。
· 若不解决源头，即使本次垫付成功，下个月风险会复发。

盲区3：未考虑地方特殊政策
· 某市（项目所在地）2025年出台了《农民工工资应急周转金管理办法》，
  规定群体性事件前30天可申请"预垫付"。
· Agent未检索该地方政策，错失了"政府预垫付+建设单位分期偿还"的更优路径。

修正指令：
· 要求主Agent在方案末尾增加"清退某鑫达劳务公司"的整改措施
· 要求主Agent将"解决建设单位拖欠源头"纳入中长期策略
· 要求主Agent补充检索并引用项目所在地的地方性工资保障政策
